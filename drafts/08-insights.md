# 综合洞察

## 架构洞察

1. Harness 有两套内核：Cordis 管可撤销的运行实例，Session Log 管不可随意撤销的历史事实。
2. Agent Loop 的复杂度来自协调边界，不来自拥有全部策略；它最重要的权力是按确定顺序提交。
3. Scope 把“谁看见注册项”和“注册项跟谁销毁”绑定到同一个 Context，减少两套所有权账本。
4. Profile / Bundle 把插件树从内部实现变成分发模型，也把 entry identity、patch 顺序与信任边界变成产品合同。
5. Capability seam 只有经过两个机械结构不同的 Provider 才算被验证；单实现接口往往只是 SDK 改名。

## 演进洞察

1. 微内核很早稳定，后续架构工作的主线是删除重复事实源、收紧 owner。
2. 三次最有解释力的反转是瞬态镜像删除、Client projection 回收至 Host、Generic Mode 退回 Plan Mode。
3. 先确定权威，再补 cache；先做具体能力，再抽共同结构。两条顺序在多个子系统重复出现。
4. Pre-release naming cleanup 不代表每次改名都是职责重构；当前证据明确说 08-13 主要是统一语言。

## 产品洞察

1. 对独立开发者，最小可采用集合是单一事实源、明确提交线、注册即清理、并发执行但有序提交。
2. Scope、Bundle DSL、热更新微内核应该由第二个 Agent / 第二种产品入口 / 第三个 Provider 的真实压力触发。
3. 可重建请求与可复现运行环境是两件事；要复现后者，还需固定插件代码、composition 与外部引用。
4. 文档的机械一致性与语义新鲜度是两个问题。生成器和 hash 不能替代反例审查。

## 证据边界

- Git 历史能说明变化，不能直接还原未写下的心理活动。
- Agent Note 解释当时的选择，当前代码决定现状。
- proposed RFC 不能因为基础设施后来落地，就被整体当成已实施规格。
- 覆盖率只对公开分母有意义，不能从核心模块推成全仓 100%。
